# 中转发现与 DeepSeek 反馈审阅

**用途：** 为 Claude 提供关于 Passport 显示“找不到中转服务器”的综合证据和既有反馈，供独立审阅。这是一份诊断备忘，不是刷机、回退或发布固件的请求。

## 摘要

当前最有力的证据指向配对之前的发现阶段：Mac 中转服务日志没有记录到来自 Passport 的发现数据报，配对数据目录也为空。检查时 Mac 正在监听预期的 TCP 和 UDP 端口，广播响应中的局域网地址与 Mac 的物理局域网网卡地址一致。普通 HTTP/SOCKS 代理不太可能影响 UDP 发现。VPN/TUN 过滤或路由器隔离仍有可能，但尚未证实。

DeepSeek 粘贴的交接记录描述的是另一个未提交的 `feature/toolbox-fixes` 工作树；当前检查的仓库中没有该工作树。其构建和主机测试结果仅由交接记录报告，真机验收明确为未执行。直接天气回退在实现并烧入设备后，可能减少对中转服务的依赖，但不能证明或修复中转发现。

## 已收集证据

以下观察除另有说明外，采集于 2026-11-19。为保护隐私，省略了具体地址、设备标识和原始日志。

- 当前检出为 `ccr-75ff76be-rli4x3` 分支的 `3f2cf3b`，工作区干净。当时本机配置里的服务器广播地址与 Mac 局域网地址一致。
- 一个 Python 进程正在监听 TCP 8787 和 UDP 8788。服务器日志记录了启动以及本机/Mac 的发现测试，但没有 Passport 的发现记录；配对数据目录没有文件。
- 已连接的 Espressif USB JTAG/串口设备与交接文档记录的 Passport 身份匹配。10 秒被动读取未收到数据；没有发送复位或烧录命令。只读句柄不允许修改串口参数。
- Mac 有活动的 `utun` 接口，但通往 Passport 局域网网段的路由走 `en1`。检查到的系统代理输出没有显示启用中的 HTTP/SOCKS/PAC 代理项。因此普通网页代理的可能性较低；VPN 客户端仍可能过滤局域网广播。
- 在受限执行环境中，本机 HTTP 探测失败，但同时观察到了监听套接字。这个结果无法判断 API 是否响应，不能据此认定中转服务离线。
- 交接文档称设备固件为 `3f2cf3b`。本次检查未能通过串口独立读取确认该版本。

## 如何理解“找不到中转服务器”

需要结合设备当前所在页面判断：

- 天气页会区分未保存 Wi-Fi、Wi-Fi 正在连接，以及 Wi-Fi 已连接但中转服务不可用。如果用户是在天气页看到“找不到中转服务器”，UI 已进入“中转服务不可用”分支。
- 信息看板页使用通用的中转不可用提示，仅凭这句提示不能确认 Wi-Fi 已取得 IP 地址。

Wi-Fi 收到 `GOT_IP` 事件后，`esp_net.c` 会调用 `relay_discover()`。设备随后通过 UDP 8788 广播；服务器回复 URL；固件再通过 HTTP 请求 `/api/hello`，遇到预期的 401 后执行配对。参见 [`esp_net.c`](../../../main/esp_net.c)、[`esp_relay.c`](../../../main/esp_relay.c) 和 [`discovery.py`](../../../server/passport_server/discovery.py)。

没有设备发现日志、也没有配对文件，说明请求没有到达服务器的发现处理器。可能原因仍包括：未保存或无效的 Wi-Fi 凭据、没有触发发现、接入点抑制广播或启用了客户端隔离、本机防火墙/VPN 过滤，或设备固件版本不符。现有证据无法区分这些情况。

## 代理与 VPN 判断

发现阶段使用 UDP 广播，不经过 Mac 的 HTTP/SOCKS 代理。后续设备到中转服务的请求使用固定局域网 URL，Mac 的浏览器代理设置不会自动应用到该请求。即使局域网路由仍走物理网卡，VPN/TUN 应用也可能过滤或抑制局域网广播。暂时暂停 VPN/TUN 后重试发现是有用的验证手段，但目前还不能称为已确认的修复。

## 对 DeepSeek 反馈的判断

粘贴的反馈声称另一个工作树里有以下改动：

- 直接请求 Open-Meteo 天气并优先使用中转服务；增加配网页扫描和高级配置。
- 每次请求单独配置 DeepSeek/OpenAI 兼容的大模型参数。
- BLE HID 报告调整和音频分析优化。

评估如下：

- ESP32-C3 没有 PSRAM，TLS 带来的内存压力值得关注；但没有设备日志或堆内存测量，卡死原因仍是假设。
- BLE 厂商报告导致初始化失败的判断尚未证实。回退报告映射可以降低复杂度，但不能证明 BLE 已修复。
- 只有相关代码存在于实际烧入的固件中，且设备能访问外部服务时，直接天气功能才能在天气页绕过中转服务；它不会修复局域网发现。
- 交接记录明确表示未执行真机测试。其构建和主机测试通过的结论仅来自该粘贴文本，本次没有独立复现。
- 反馈所述 API key 明文保存在 NVS，并通过局域网 HTTP 传输，是采用这些改动前必须评估的安全取舍。

当前检出的代码没有 `main/esp_weather.c`，本地也没有 `feature/toolbox-fixes` 分支或工作树；检查到的固件和服务器源码中也没有 DeepSeek 覆盖请求头。不要假设粘贴反馈中的改动已经安装到 Passport。

## 建议的诊断顺序

1. 查看 Passport 设置页里的 Wi-Fi 和中转服务状态。不要分享 Wi-Fi 密码。
2. 暂时暂停 VPN/TUN，在天气页按 OK 重新查找；观察服务器是否记录来自设备的发现请求，以及中转状态是否变化。
3. 若 UDP 发现仍缺失，可通过当前配网页的可选服务器地址栏，测试直连 `http://<Mac局域网地址>:8787`。直连成功则可把问题缩小到发现/广播。当前配网页会同时保存 Wi-Fi 信息和服务器地址，因此需重新填写现有 SSID 与密码；密码留空可能覆盖已保存的密码。
4. 若直连 HTTP 也失败，再检查 TCP 8787 可达性、Mac 防火墙和路由器客户端隔离。先区分传输层问题，再考虑改固件。

## 请 Claude 核查

- 当前固件在 Wi-Fi 获取 IP 后是否可靠地触发服务器发现，包括首次尝试失败后？
- 不复位或烧录设备，怎样用最少的观察区分 Wi-Fi/IP 未就绪、UDP 广播被拦截和 TCP 中转请求失败？
- 配网页的手动服务器地址能否作为诊断绕行方案？需要说明哪些 NVS 副作用？
- DeepSeek 的哪些改动值得分开审阅？要取得什么证据，才能把 BLE/卡死修复视为完成？
