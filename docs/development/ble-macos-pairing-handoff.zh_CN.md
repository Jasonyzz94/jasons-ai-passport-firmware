## 已观察到的现象

遥控页面将 NimBLE 启动为可连接的 BLE HID 键盘。macOS CoreBluetooth 能收到 `Passport-10C0` 的广播，其中包含 HID 服务（`0x1812`），RSSI 较强。因此可以排除未开启广播、不可连接模式以及单纯的距离问题。

macOS 蓝牙服务日志显示，从“蓝牙设置”发起的连接曾成功完成。GATT 服务发现也已完成，系统识别出 BLE 键盘并订阅了 HID 报告特征。按键时，设备端也产生了 GATT 通知。

但 macOS 同时报告 `lePaired=0`，且链路未加密。随后设备端主动断开，临时安全密钥被清除。因此“蓝牙设置”可能一直停留在“正在连接”，无法形成可绑定、可重连的 HID 设备。

**GATT 连接成功和出现 HID 通知，并不等于配对、加密、绑定或端到端键盘输入已经验收。** 不要仅凭 `retrieveConnectedPeripherals` 判断这类由系统持有的 HID 连接；还要结合蓝牙服务时间线和真实按键输入。

## 根因

### 1. 未启用 HID 安全要求

`sdkconfig.defaults` 开启了安全连接及绑定相关的运行时行为，但没有设置 `CONFIG_BT_NIMBLE_SM_LVL`，因此 ESP-IDF 使用 NimBLE 默认级别 `0`。

NimBLE HID 服务只有在 `BLE_SM_LVL` 为 `2` 或 `3` 时才添加加密读写标志。级别为 `0` 时，macOS 无需配对即可发现服务并订阅，这与本次观察到的未加密、未绑定连接一致。

### 2. 应用未在连接后主动发起安全配对

[esp_ble.c](../../main/esp_ble.c) 中，`BLE_GAP_EVENT_CONNECT` 成功路径没有调用 `ble_gap_security_initiate()`，只在连接失败后重新广播。手机可能主动发起安全配对，而 macOS 可能等待加密要求，因此实现不能依赖某一种中心设备的行为。

### 3. HID 初始化重置 GAP 设备名

应用在 `esp_hidd_dev_init()` 之前设置 GAP 名称。ESP-IDF 的 NimBLE HID 初始化随后调用 `ble_svc_gap_init()`，把名称恢复为默认值 `nimble`。广播数据仍包含 `Passport-10C0`，所以 macOS 可能为同一设备显示不同名称。

设备信息服务还报告了模型号 `NimBLE`。如果产品不希望系统详情中出现协议栈默认值，需要单独检查并设置该字段。

## 必须实施的修改

1. 设置 `CONFIG_BT_NIMBLE_SM_LVL=2`，使用不要求 MITM 的 Just Works 加密配对，并保留安全连接、绑定和 NimBLE NVS 持久化。
2. GAP 连接成功后，如果链路尚未加密，主动发起安全配对。明确处理调用错误和配对失败，避免重复发起，同时保留现有的重复配对恢复逻辑。
3. 在 HID/GAP 服务初始化完成后、开始广播前设置 GAP 设备名；如有需要，同时设置明确的 DIS 模型号。验证广播本地名称和 macOS 读取到的名称。
4. 在适合的情况下为连接状态决策增加主机测试，但主机 mock 不能作为 macOS 配对成功的证据。
5. 保持现有单连接、内存、Wi-Fi 让出以及停止/重启生命周期约束。刷写前运行完整仓库验证。

## 真机验收

- 删除电脑上的旧配对记录，再从 macOS“蓝牙设置”配对。确认链路已加密并完成绑定，而不只是 GATT 就绪。
- 按实际功能验证 Mac 收到导航、演示、媒体、修饰键和文本输入。串口出现 `GATT notify` 本身不算验收。
- 退出并重新进入遥控页面，重启 Passport，确认可以重连，且不会出现重复或陈旧的 `nimble` 记录。
- 在一个主机上忽略设备后重新配对，覆盖重复配对恢复；同时回归测试手机配对与输入。
- 确认广播和系统设备详情一致使用 `Passport-10C0`。
- 需要保留 NVS 时使用兼容分区布局的分段刷写，并确认更新后已保存的 Wi-Fi 配置仍可使用。

## 环境说明

诊断时测试 Mac 的可用磁盘空间严重不足。评估配对记录持久化前，应先保证足够的可用空间。原始日志可能包含已保存的网络名称、设备地址和本机用户信息；应只保留在本机，或在脱敏后再分享。
